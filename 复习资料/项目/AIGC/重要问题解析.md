## 1、外部大模型管理平台

### （1） token 制下如何选择要路由到哪个资源

我们 token 制下的资源路由不是简单随机挑一个 url 和 apikey，而是做了分层路由。
- 先按模型实现路由，决定走哪套模型实现（OpenAI / Claude / Gemini / Qwen 等）
- 第二层再按 modelKey 进入该模型对应的普通资源池，这些资源池本质上是平台统一维护的一组 url + apiKey 配置。
- 从 Redis quota ZSet 中挑出剩余额度足够的 key，这里会先预估出此次请求所需 token 资源，然后找出剩余 token 满足的 key。如果筛出来有多个可用资源，不是直接随机，而是再做一层稳定分配：
  - **粘性路由**：有用户标识时，会基于 userId + modelKey 做粘性哈希，让同一个用户尽量稳定命中同一个资源。公式是：hash(userId + "#" + modelKey) % totalWeight
  - **加权随机**：如果粘性路由失败，就按配置权重做加权随机，保证流量分布更均衡。
- 如果当前所有 key 的剩余额度都不满足，也不会立刻失败，而是为了保证可用性回退到全量候选池，再走一轮粘性或随机选择。所以这套逻辑本质上是“优先选额度充足的资源，不够时再做兜底放量”。
- 请求完成后，平台会根据这次实际使用的 totalToken 去扣减该 key 在 Redis 里的额度；同时后台定时任务会周期性重建各模型的 quota 池。

token 制资源路由，而是同时兼顾三件事：
- 资源额度可用；
- 流量分布稳定；
- 上游异常或额度不足时平台仍然尽量可用。

#### （1）细节 1：本次请求所需 token（maxTokens）是怎么计算的？

这里的 maxTokens 不是一个固定值，也不是全平台统一一套算法。它本质上是：平台在路由前，用来估算“这次请求大概会占用多少 token 额度”的一个阈值。

**一种口径：promptTokens + max_tokens**
- **输入 token 预估值**：promptTokens，它取决于这次请求的输入内容有多少，比如：system prompt 多长、历史对话有多少轮、用户这次问题多长、有没有图片、工具说明等附加内容
- **输出 token 上限**：max_tokens，它一般来自这次请求参数，或者来自平台/模型配置的默认值和上限控制。用户可能传 1024、2048，不同模型也可能有不同默认最大输出上限。

**另一种口径，只看 maxTokens**
还有些实现不会把 promptTokens 算进去，而是更偏向拿：
- 本次请求声明的 maxTokens
- 或者模型允许的最大输出上限

#### 细节 2：（2）不存在满足的资源为什么还要进行另一次粘性路由+加权随机

因为平台侧 Redis 里的 quota 只是一个近实时近似值，不是厂商真正的官方实时剩余额度。如果平台太死板，可能会把本来还能成功的请求直接挡掉。所以它是在“控风险”和“保可用”之间取平衡，优先挑更安全的资源，兜底时允许继续尝试

最终有没有超，要看上游厂商那一刻的真实 TPM / RPM / 并发状态，如果厂商判定超限，可能返回：
- 429
- 供应商自定义限流错误
- 临时拒绝 / 配额不足类错误

这里这个 TPM 一般是基于厂商提供或运营确认的能力上限，在平台侧做成配置化额度。

#### 细节 3：（3）厂商的额度限制为什么一分钟刷新一次

因为大多数厂商对 token 限制，天然就是分钟级配额思路，比如：
- TPM：tokens per minute
- RPM：requests per minute
所以你们平台用 Redis 维护这份 quota，本质上是在本地模拟一层“分钟级额度桶”。

逻辑可以理解成：
- 每个 key 初始化一个分钟级可用额度
- 请求完成后，按真实 totalToken 扣减
- 到下一个刷新周期，再把额度恢复 / 重建

这样做的目的就是：尽量把单个资源在一分钟内的使用量控制在其能力上限附近，避免把所有流量都打爆到上游。

不过这里要注意一个细节：从工程上讲，这种刷新通常只是近似控制，不是严格等同厂商的真实滚动窗口。因为很多厂商实际可能是：
- 滚动 60 秒窗口
- 不同模型/账号有不同策略
- 还叠加 RPM、并发限制等


### （2）席位制下如何选择要路由到哪个资源

席位制和 token 制最大的区别，不是接口长得不一样，而是底层调度和商业模式不一样。

token 制更多是按调用量和 token 额度做路由，而席位制本质上是厂商按 seat / 人头售卖资源，我们把厂商提供的一批真实 seat 资源入池，然后平台按**系统、模型、用户**去调度这些资源。所谓的 seat 也是一组 apikey+url，然后里面包含可以调用的不同的模型，只是这组 apikey+url 计费方式是按月席位数收费。

在实现上，平台会先根据 appKey + modelKey 查配置中心，看这次请求是否命中某个 poolCode；如果命中，就进入席位池调度。席位池里每条资源会配置真实的 apiKey、apiUrl、max_user_count、seat_code，以及 model_configs。其中 model_configs 很关键，它决定这个 seat 支持哪些模型、这些模型在厂商侧真实叫什么名字，以及后续计费归因用哪个模型编码。

具体调度时，第一步会优先复用用户当前已绑定的 seat；第二步如果活跃绑定过期了，会尝试复用用户最近一次用过的 seat，做亲和性复用；如果这两步都失败，才会从池里挑最空闲的一批候选资源，再随机选一个做原子抢占。

并发控制靠 max_user_count 和 Redis + Lua 做，能保证同一个 seat 同时服务的用户数不会超过配置上限。

另外席位池还有一套 429 冷却机制。如果某个 seat 命中了厂商账号级限流，不会整个池子失败，而是把这个资源临时冷却摘流，调度层重试时通常会切到其他 seat。这里冷却不是单独用一个 key 存，而是复用了容量 ZSet，用负分表示“冷却到什么时候”，到期后自动回池。

从商业模式上讲，席位制通常不是按 token 实时结算，而是按 seat 按月或按账期收费，平台侧更关注的是资源池化调度、并发容量控制、用户绑定稳定性和席位利用率。

至于模型选择，席位制下当然也可以指定想用的模型，但前提是当前池里的 seat 资源支持这个模型，也就是得在 model_configs 里声明过，平台再把标准模型名映射成厂商真实模型名去调用。

#### （1）细节1：优先复用 / 亲和性复用的理解

优先复用Redis 里有一个 USER_BINDING_KEY，记录：uid -> resourceId，这个 key 有 TTL，只要这个 key 还在，并且对应资源没冷却还可用，支持当前模型，平台就直接续约并继续使用这个资源

所以“优先复用”本质上是：用户当前还处于活跃绑定期，就继续使用同一个 seat 资源。

亲和性复用核心还是复用同一个 USER_BINDING_KEY，区别在于它的 TTL 设计分两段：
- 活跃租约时间 leaseSeconds，表示“当前确实占着这个 seat”
- 亲和保留时间 affinityTtlSeconds，表示“活跃占用虽然过期了，但 user -> resource 这条映射先别马上删，再保留一段时间，方便后续优先回到原 seat”

所以更准确地说：USER_BINDING_KEY 并不是“只要 key 还在就一定活跃占用”，有可能只是“历史偏好仍保留”。而真正判断用户是否还活跃绑定，还要结合：RESOURCE_USER_ZSET_KEY 里该 uid 是否仍在这个资源的活跃用户集合里。

**优先复用 = 当前活跃绑定仍然存在；
亲和性复用 = 活跃绑定已过期，但 user->resource 的历史偏好还保留着，平台优先尝试把这个 seat 再分给他。**

#### （2）细节 2：从最空闲窗口里抢占资源 是什么意思

所以“从最空闲窗口里抢占资源”的本质是：先从 ZSet 里拿出 score 最小的一批资源，也就是当前占用人数最少的前 N 个资源
再过滤：**冷却中的、停用的、不支持该模型**的，最后从这批候选里随机挑一个做占用。

为什么不是直接选最小的那个？

因为如果所有请求都永远选最小值，会有两个问题：所有人都打同一个资源，**形成热点，高并发下会发生惊群**。

所以你们实现是：先按“最空闲”缩小候选窗口，再在窗口里随机选一个，这是一种典型的：“**最小负载优先 + 小范围随机打散**”

#### （3）细节3：CAPACITY_ZSET_KEY 这个 ZSet 的结构和“负分冷却”原理

CAPACITY_ZSET_KEY 它是一个 Redis ZSet，结构可以理解成：
~~~ text
key = openai:pool:{poolCode}:cap
member = resourceId
score = 资源当前状态
~~~

一个 poolCode 对应一个容量 ZSet，里面每个 member 是一个 seat 资源的 resourceId，score 不是固定含义，而是“复用编码”的状态值。
- score >= 0 时，score = 当前活跃绑定用户数，用于取最空闲资源；
- score < 0 时，score = - cooldownExpireAt，资源当前处于冷却中，负数的绝对值就是“冷却结束时间戳”

席位池资源命中账号级 429 后，会被写入冷却状态，具体做法是把它在容量 ZSet 里的 score 改成一个负数，负数的绝对值表示冷却结束时间戳。后续每次该 pool 再发生资源分配时，调度器都会先扫描一遍冷却资源，如果发现某个资源冷却时间已经到了，就把它的 score 恢复成当前真实的活跃绑定用户数，让它重新回到候选池里。所以这套恢复机制不是依赖单独定时任务，而是基于请求驱动的按需恢复。

#### 细节4：当前 pool 的情况以及 pool 与 seat 的对应关系

当前支持的账户池有：阿里云、火山、kiro、github-copolot，然后一个账户池对应很多个 seat 资源，一个资源都有一个最大服务用户数以及当前绑定用户数。

### （3）请求费用限流+次数限流的原理

目前包含几个限流的方式：时段限流、费用限流、断流状态、外部接口次数限流。实际代码里的排列顺序是
~~~text
系统鉴权 / 模型权限
-> 断流状态检查(checkCutoff)
-> 时段限流 + 费用阈值(flowControl / flowControlByTimes)
-> 外部接口次数限流(system-user-model)
-> 才真正进入模型路由和上游调用
~~~

#### （1）时段限流

**时段限流：控制“某系统对某模型在某个时间段能打多少次**

请求进来后会生成一个限流 key：`chat:limiting:{system}:{model}:{timeSlot}`，这里的 timeSlot 用的是当前时间的分钟粒度字符串（代码里 DateStyle.HH_MM_CN），本质上就是按“当前分钟桶”计数。

然后它会从缓存里面取当前分钟内该系统+模型的调用次数
对比该时段配置的 rateLimitPerMinute，超过就抛：CHAT_GPT_LIMITING。

这里的时段次数阈值的配置来源有明确优先级：
- DB 配置，读取 DB 的限流配置到缓存
- 第二优先级：Apollo / 配置中心
- 第三优先级：默认值

#### （2）费用限流

**费用阈值：控制“某系统对某模型当天花了多少钱”以及控制“某系统所有总费用是否超过其预算总量“。**

费用阈值的获取逻辑和时段限流一样，获取到某个系统对某个模型的日费用限额值 dailyCostLimit，以及某些系统的总预算值 totalCostLimit。

随后计算费用，统一计费策略层支持的典型维度有：
- token
  - 输入 token
  - 输出 token
  - 联网搜索、cache read / write、thinking token、action usage
- frequency / 次数
- duration / 时长
- characters / 字符数
- drawings / 图片张数
- composite / 组合计费


超阈值后的行为：费用控制不是只做硬拦截，它还带告警分档：
- 80%：预警
- 100%：拦截

#### （3）断流处理

**控制“这个系统是不是已经被账务侧判定停服了”**

断流不是请求线程实时算出来的，而是后台账务/欠费任务根据系统余额、告警额度和告警时长异步计算后，把系统标记成 isCutoff=1，前台请求只读这个状态位做硬拦截。

**费用限流是实时预算控制，断流是后台账务任务打标后的停服开关。**


#### （4）次数限流

**次数限流：控制“某个用户今天对某个模型还能调多少次”**

这个和前面 3 个最大的区别是：
- 前面是“系统级 / 模型级 / 预算级”
- 这个是“用户级 / 外部接口级 / 次数级”

它的 key 是：`openai:external:call:limit:{date}:{system}:{user}:{model}`，包含日期、系统、用户、模型。

它用 Lua 保证原子性：
- key 不存在 -> set 1 + TTL
- key 已存在且 < quota -> incr
- key 已达到 quota -> 返回负数，抛限流异常

限额阈值的获取逻辑：
- 第一步：先取 system 级默认额度
- 第二步：看 user 维度有没有单独额度
- 第三步：看 model 维度有没有单独额度

这种场景里常见诉求不是“不同维度互斥回退”，而是：
- 默认所有人每天 100 次
- 某个重点用户给到 500 次
- 某个重点模型给到 300 次

**那就希望最终配额取更宽松的那个，而不是被更小的默认值覆盖掉。**

#### （5）次数限制和费用限制会不会出现超额使用？项目里怎么避免？

**次数限流：理论上比较准，超额风险小**

外部接口次数限流走的是：
- system + user + model + day 维度
- Redis + Lua 原子计数
- 达到 quota 就直接拒绝

这里因为 Lua 是原子执行的，所以同一个 key 下并发竞争不会把次数打穿。所以次数限流这条链路，精度是比较高的。

**费用限流：有可能出现轻微超额，属于最终一致性治理**

费用阈值控制和次数限流不一样，它不是纯计数，而是“**先调用，再累计费用，再用于下一次请求拦截**”。

由于费用很多时候是请求完成后才知道，所以费用不是请求一进来就能精确扣掉的。另外，项目里费用累计本身是“在线缓存 + 异步落账”，也就是：
- 请求先成功返回
- 调用明细和费用随后异步计算/上报
- Redis / 缓存里的日累计费用再被后续请求拿来做阈值校验

**这意味着在高并发下，短时间内可能会有少量请求同时放过去，导致预算轻微穿透。**

#### （6）费用计算和调用是不是异步的

结论：**一半是实时读缓存做治理，一半是请求后异步计算/上报**

实时的部分，请求前会做：
- flowControl
- 读取当日累计 usage / fee 缓存
- 判断有没有超过阈值

异步的部分，请求完成后，会：
- 落 chatgpt_main 等明细
- 根据模型和计费口径计算本次费用
- 异步上报智数平台
- 更新日累计 usage / fee 缓存
- 进入日/月聚合账单链路

所以你可以理解成：
- **请求前：用“当前已累计数据”做实时治理**
- **请求后：把“本次新增费用”异步补到统计和账务体系**

### （4）大模型接口接口如何做并发控制

大模型接口并发控制本质上是：
- 入口前置治理：先挡掉不该进来的流量
- 系统 / 用户维度限流：控制请求速率和调用次数
- 资源池调度控制：控制具体上游资源的承载量
- 异常摘流与重试：上游资源不稳定时快速切换，避免雪崩

#### （1）第一层：系统级前置拦截，先控总量

请求进入后，不会立刻打上游，而是先做一套前置治理：
- 模型权限
- 黑名单
- 时段限流
- 费用阈值
- 断流
- 外部接口次数限流

**先把明显不该继续进入模型调用链路的请求挡掉，避免把流量直接压到资源池和上游厂商。**

#### （2）第二层：Token 制资源池控制，控制资源分流

如果走的是普通 token 资源池，平台会按：
- modelKey，先按 modelKey 找资源池
- 剩余额度，优先选额度足够的 key
- 粘性路由，有 userId 就粘性路由
- 权重，没 userId 就加权随机
- 冷却状态，上游 429 时做冷却切换

去选择具体的 url + apiKey。

**不直接限制“同时只能多少个线程”，而是通过配额、路由、冷却来避免某个 key 被瞬时打爆**


#### （3）第三层：席位制资源池控制，控制真实资源占用人数

如果命中席位池，这部分就不是软控制了，而是比较明确的容量控制。分配流程是：
- 优先复用当前绑定
- 再尝试亲和性复用
- 再从最空闲资源窗口里抢占
- 如果某 seat 满了，就换别的 seat

这层其实就是“硬并发控制”，对席位资源做真实的并发槽位控制。

#### （4）第四层：429 冷却摘流，避免异常资源放大并发问题

无论 token 制还是席位制，项目里都有一个很重要的稳定性手段：上游资源命中账号级 429，平台就把这个资源冷却摘掉，后续请求不再优先打这个资源，然后重试切换到其他资源

席位池里是通过 CAPACITY_ZSET_KEY 的负分冷却做的；

OpenAI 外部兼容链路还会捕获 OpenAiPoolRetryableException 再重试一次。

这层控制解决的是：**当某个资源实际承载已经不行时，不让后续并发继续堆上去。**

#### （5）异步图片 / 视频 / 音频链路：并发控制怎么做

异步任务链路不像同步聊天接口那样“请求进来立刻返回结果”，它更像：
- 提交任务
- 进入处理中
- 抢占资源槽位
- 发起上游任务
- 回调 / 轮询收结果

提交和处理分离，不会让所有请求线程都同步阻塞在上游任务上。

某些视频 / 图片生成任务在真正调用上游前，会先判断当前模型资源还能不能再接新任务。如果没抢到槽位：
- 排队
- 等待
- 或直接失败 / 稍后重试

正常任务、重试任务、回调补偿任务会拆开，避免某一类流量把整个处理链路拖死。所以异步链路更像：
- 任务队列 + 槽位控制 + 状态机 + 补偿
