# Nginx-Sphere 简历项目面试回答版

## 1. 负责整体架构设计

### 面试官可能会问：你先整体介绍一下这个项目，以及你的架构设计思路

这个项目叫 Nginx-Sphere，是公司内部自研的一套企业级 Nginx 全生命周期管理平台，主要解决传统 Nginx 运维里几个很典型的问题：第一是实例分散，南海、贵安、多个云环境里都有，规模在 5000+；第二是配置分散，很多都是登录机器手工改，出了问题回滚困难；第三是缺少统一的安装、发布、监控和服务化纳管能力。所以我们做了这套平台，目标就是把 Nginx 从“机器级人工运维”升级成“平台级统一管控”。

我当时在架构上把系统拆成三层：管控层、下发层、执行层。管控层是 `lb-sphere`，基于 Spring Boot，负责页面、权限、配置编辑、操作编排和任务状态管理；下发层通过 NATS 做异步指令分发，解决高并发下发和回调解耦问题；执行层是部署在边缘侧的 Rust Agent，负责本地执行 `nginx -t`、reload、配置写入、回滚、状态采集这些动作。这个分层的核心考虑是把“业务编排”和“本地执行”彻底解耦，这样控制面只负责发意图，不直接碰机器，平台的可扩展性和稳定性都会更好。

另外这个项目还有一个比较有代表性的点，就是我把 VM 模式和 K8s 服务化模式统一纳入了一套平台里。VM 模式下，平台通过 Agent 去纳管传统宿主机上的 Nginx，适合存量系统平滑收编；K8s 模式下，我们对接 MWFE 底座和 Helm Chart，把 Nginx 做成服务化实例，支持用户一键购买、自动拉起 Pod、自动扩缩容。虽然底层运行环境完全不同，但上层的配置模块、任务单、回滚、差异比对这些能力是尽量复用的，所以整体做到了比较高的代码复用率，也避免了维护两套完全独立系统。

### 面试官可能会问：控制台是多实例部署的，你怎么避免定时任务重复执行、消息回调错乱这些分布式问题

这块我当时重点解决了两个问题。第一个是定时任务重复执行。因为控制台是双活部署，而且单机房内部也会多 Pod 横向扩容，Spring 的 `@Scheduled` 默认只感知当前 JVM，不感知集群，所以像 CMDB 同步、Agent 升级扫描、心跳超时检测这类任务会重复跑。我的处理方式是引入 Redis 分布式锁，通过 `SET NX PX` 或 Redisson 的 `tryLock` 实现全局抢占，同一时刻只能有一个 Pod 执行。释放锁时依赖 Lua 脚本对比 UUID，防止锁超时后误删别人的锁，这样在双活和多副本场景下都能稳定工作。

第二个问题是控制台和 Agent 通过 NATS 通信时，如果控制台是多 Pod，响应很容易串。我的做法是每次请求都生成一个全局唯一 UID，控制台先订阅这个 UID 对应的回调主题，再把 UID 作为 reply-to 发给目标 Agent。Agent 执行完以后，把结果直接发回这个 UID 主题。这样无论后端扩多少个 Pod，回调一定会回到最初发起请求的那一个 Pod，不会出现“Pod A 发请求，Pod B 收响应”的错乱问题。这其实是一个典型的分布式异步 request-reply 设计。

### 面试官可能会问：你们控制台双活架构是怎么做的，高可用怎么保证

我们的控制台部署在南海和贵安两个机房，通过 APISIX 做统一流量入口和负载均衡，两边 Pod 同时对外服务。MySQL 和 Redis 当前主要部署在贵安，控制台通过专线访问。Redis 主要承担分布式锁和共享状态的职责；MySQL 负责任务单、配置模块、实例状态这些核心数据。这个架构在当时资源条件下已经实现了控制面的双活，但我也清楚它的边界，比如南海机房比较依赖贵安的数据层，所以后续我也给出了优化方向，比如读写分离、Redis 本地只读副本、数据库自动切换等。

如果从高可用角度总结，我做了四层保障：第一是控制台无状态化，多副本、跨机房部署；第二是 MySQL/Redis 高可用和状态外置；第三是 NATS 作为异步通信总线，减少耦合和阻塞；第四是 Agent 心跳、任务状态、告警和超时隔离，做到故障可感知、可隔离、可恢复。

## 2. 完成复杂配置解析性能调优（Go Sidecar + UDS）

### 面试官可能会问：为什么你要单独做一个 Go 解析服务，Java 解析不行吗

这个事情的背景是，Nginx 配置文件有些场景会非常大，十万行级别并不罕见。最开始控制台的配置解析和结构化渲染是用 Java 做的，但随着配置规模变大，解析延迟、页面编辑卡顿都很明显。尤其我们的控制台本身是异地双活部署，如果解析服务单边部署，会碰到跨机房访问、防火墙策略、网络抖动这些问题；如果两边都单独部署一套，又会增加运维复杂度和一致性成本。

所以我最后的方案是把解析能力拆成一个高性能 Go 服务，并且直接作为 Sidecar 和控制台部署在同一个 Pod 里。这样做的好处有两个：第一，Go 对这种纯文本流式处理、状态机解析的场景更轻，吞吐更高；第二，控制台和解析服务都在同机 Pod 内，可以直接走本地 IPC，不需要经过机房网络。

### 面试官可能会问：你说用了 UDS 替代 HTTP，这个优化到底解决了什么问题

UDS，也就是 Unix Domain Socket，本质上是本机进程间通信。之前如果走 HTTP，即使是在同一台机器上，还是要走一遍网络协议栈，涉及 TCP 建连、序列化、内核网络层处理这些额外开销。后来我把控制台和 Go 解析服务改成通过 `.sock` 地址建立本地 socket 连接，双方通过内核缓冲区直接交换字节流，绕开了 HTTP/TCP 的很多固定成本。

这个改造的价值主要体现在两个层面：第一是性能，平均解析延迟从大概 50ms 压到了 0.1ms 级别，性能提升非常明显；第二是架构简化，因为 Sidecar 和控制台同 Pod 部署，不再依赖跨机房网络访问，自然也避开了很多防火墙和链路问题。最终效果就是十万行级别配置也能快速完成结构化解析和前端渲染，编辑体验上不再有明显卡顿。

### 面试官可能会问：你怎么保证这种解析方案在双活部署下仍然稳定

这里我的核心思路是“把跨机房问题消灭在设计里”。不是去想办法让南海的控制台跨机房调贵安的解析服务，或者反过来，而是让每个控制台 Pod 自带一个解析 Sidecar。这样无论请求被路由到哪个机房、哪个 Pod，解析都发生在本地 Pod 内部，不依赖外部网络。控制台只需要和自己的 Sidecar 通信，所以不会因为防火墙策略或链路延迟导致解析链路不稳定。

从工程上看，这个方案其实也是典型的“伴生服务本地化”设计：把高频、低延迟、强耦合的能力贴近主服务部署，用本地通信替代远程通信。

## 3. 负责平台底层核心 Nginx-Agent 的架构设计与迭代开发

### 面试官可能会问：为什么 Agent 要用 Rust 写，而不是 Java 或 Go

我当时选择 Rust，核心考虑是它更适合做常驻边缘进程。Agent 是部署在每一台 Nginx 宿主机上的，不是中心服务，所以对资源占用、稳定性和长期运行的可靠性要求非常高。Java 的运行时太重，JVM 对这类小而多的驻留进程不友好；Go 虽然够轻，但在我当时关注的内存可控性、并发细粒度控制和安全性上，Rust 更适合。最终这套 Agent 基于 Rust + Tokio 实现，内存稳定在 10MB 左右，对宿主机 CPU 影响也很低。

更重要的是，Rust 的所有权和类型系统天然帮我规避了很多边缘进程最怕的问题，比如内存泄漏、悬垂引用、并发状态错误，这些问题一旦出现在批量部署的 Agent 里，排查成本会非常高。所以从长期可维护性角度，我觉得 Rust 是合理的。

### 面试官可能会问：Agent 的核心能力都有哪些

Agent 主要做四类事情。第一类是指令执行，比如 reload、restart、start、stop、配置写入、回滚、`nginx -t` 语法校验等；第二类是通信能力，通过 NATS 订阅自己的 instanceId 主题，接收控制台指令并异步回调结果；第三类是状态采集，比如周期性心跳、版本信息、进程状态；第四类是安全控制，比如配置写入前的预检、灰度执行和回滚兜底。

在实现上，我通过 Tokio 把每个 NATS 指令处理成独立异步任务，做到并发隔离，避免一个慢命令阻塞其他请求；同时给网络断连、自恢复、超时回调等都做了机制设计，让 Agent 能够比较稳定地在复杂网络环境下长期运行。

### 面试官可能会问：你提到跨防区自动安装 Agent，这个具体怎么做的

这个问题是实际生产里很典型的一个坑。有些机器在 DMZ 或隔离防区，拿不到 OSS 上的安装包，导致传统“控制台下发安装脚本，机器直接去拉包”的方案走不通。我的处理方式是设计了一套“跨区域分发代理”方案：先由可达区域的节点或中转代理拿到安装包，再通过受控链路转发给目标机器，最终仍然由控制台统一编排安装流程。

这样做的价值在于两点：第一，安装链路从“目标机必须直连 OSS”变成“目标机只需要能连代理或既有通道”，适应复杂网络环境；第二，平台侧的操作体验没有变，用户仍然是在控制台发起安装，但底层分发机制更灵活。落地后，版本更新和批量安装从小时级缩短到了分钟级。

## 4. 主导 Nginx 服务化部署落地与架构演进

### 面试官可能会问：你们的 Nginx 服务化到底是怎么做的

我的核心工作是把 Nginx 从传统宿主机形态演进成 K8s 下的服务化实例。具体方案是 `Nginx + Agent Sidecar` 的双容器 Pod 形态：一个容器跑 Nginx 主进程，另一个容器跑 Agent。这样 Agent 仍然保留原来对配置下发、reload、回滚、状态采集的能力，只不过执行对象从宿主机进程变成了同 Pod 里的 Nginx 容器。

在交付方式上，我把 Nginx 镜像、Agent 镜像、ConfigMap、Service、Deployment、资源规格、NATS 配置这些都收敛成标准 Helm Chart，然后对接公司 MWFE 服务化底座。最终用户侧的体验就是：在购买界面一键下单，MWFE 触发底层 K8s 自动创建对应 Pod，平台再通过回调同步实例信息、Pod 列表、入口信息和后续配置任务。也就是说，我把“租户下单 -> 底层拉起 -> 服务纳管”这条链路打通了。

### 面试官可能会问：为什么容器里还要放一个 Agent Sidecar，不能只跑 Nginx 吗

如果只跑 Nginx，那它只是一个普通业务容器，没有纳管能力。我们平台最核心的价值并不是“把 Nginx 跑起来”，而是“对 Nginx 做统一配置管理、下发、回滚、状态采集和弹性变更”。这些能力原来在 VM 时代是靠 Agent 完成的，所以到了容器化阶段，我的思路不是重写一整套新机制，而是保留 Agent 作为控制执行面，把它伴生到 Pod 里。

这样做好处很明显：第一，复用了 VM 模式下大量成熟的执行逻辑和通信模型；第二，平台上层对 VM 和 K8s 的管控能力可以尽量统一；第三，后续扩容、漂移、重建时，Agent 可以继续承担配置恢复和本地控制职责。

### 面试官可能会问：容器是随建随毁的，怎么保证配置不丢

这其实是服务化改造里最关键的问题之一。宿主机时代配置天然在磁盘上，机器不销毁配置就不会丢；但 Pod 是易失的，漂移、重建、扩缩容都会导致原容器消失。所以我的设计思路是：配置不能再依赖 K8s 节点本地磁盘，而必须以管控平台为配置真源。

具体做法是，配置模块的完整内容保存在平台侧数据库里；Pod 启动后，Agent Sidecar 拉取平台上的最新全量配置，写入共享卷或指定配置目录，然后拉起 Nginx 主进程。后续如果发生回滚、扩容、新 Pod 拉起，也都走这套“平台是真源、Pod 本地是副本”的机制。这样即使某个 Pod 被销毁重建，也能把配置完整恢复回来，避免因为容器漂移导致配置丢失。

### 面试官可能会问：扩缩容、购买、删除这些服务化生命周期事件，你们怎么跟平台联动

这一块我接入了 MWFE 的回调机制。用户在服务化平台发起购买、扩容、缩容、删除后，MWFE 会通过回调通知我们的平台当前实例状态。控制台收到回调后，会去 MWFE 查询最新实例详情，再把集群基础信息、入口信息、Pod 信息同步到本地库里。比如扩容时，我会识别新增 Pod，并补做配置同步；缩容时，会把消失的 Pod 做软删除和状态更新；删除时，则把整套实例和 Pod 状态标记为已删除。

所以从平台视角看，服务化实例不是一个黑盒，而是一个可被持续感知、可被配置、可被回滚、可被追踪的受管对象。
