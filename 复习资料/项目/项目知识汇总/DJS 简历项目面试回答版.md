# DJS 简历项目面试回答版

## 1. 主导 PaaS -> GNC 架构升级与模块重构

### 面试官可能会问

- 你们为什么要把 PaaS 调度平台升级成 GNC？
- 这次架构升级的核心变化是什么？
- 这次改造带来了什么收益？

### 标准回答

我这块主要做的是把原来 PaaS 调度平台升级成云原生的 GNC 体系。PaaS 时代的核心模块是 `center + api + executor`，单区域场景下能工作，但在多地域、多环境、跨网络隔离和平台统一治理上存在几个明显问题：第一，它更偏单区域部署，历史上主要集中在佛山；第二，跨区域访问和调度链路不统一，网络成本和运维成本高；第三，调度侧依赖 Akka 事件驱动分片，在节点抖动、网络分区时稳定性不够理想。

所以到了 GNC，我们做了两层升级。第一层是架构分层，把原来“管理、触发、治理”这几类能力拆成更清晰的三层：全局入口层、区域控制面和区域调度面。全局入口层负责统一入口和区域路由，比如 `console-cloud / APISIX / region-service / portal`；区域控制面就是 `dashboard`，负责配置管理、统计、治理任务；区域调度面就是 `schedule/trigger`，负责真正的任务扫描、路由和下发。第二层是部署形态升级，把原来偏单区域的平台，改造成多区域独立部署，每个区域都有自己的控制面、调度面和运行态数据，区域内闭环，区域间通过入口层做路由。

这样做的直接好处有三个。第一，多区域隔离，单区域故障不会拖垮全局。第二，海外和异地用户可以就近访问控制台和调度链路，延迟更低。第三，平台职责更清晰，后续做调度优化、网络适配、协议演进都会更可控。

### 可继续展开的细节

- PaaS 更像“平台化过渡版本”，GNC 更像“真正产品化、云原生化版本”。
- 区域独立部署后，佛山、贵安、欧洲、新加坡都可以独立调度、独立治理。
- 入口层统一之后，前端访问和后端 API 路由不再耦合到单个区域。

### 一句话成果

把原来仅支持佛山单区域的调度平台升级为多区域独立部署架构，实现故障与流量按区域隔离，显著降低单区域异常对全局调度的影响。


## 2. 调度侧分片机制重构

### 面试官可能会问

- 你们为什么把 PaaS 的 Akka 分片机制换掉？
- GNC 的固定分桶机制是怎么做的？
- 这种机制相比以前有什么优势？

### 标准回答

PaaS 时代调度侧主要依赖 Akka 集群事件来做分片。它的思路是节点上下线后，通过 Akka 的 `MemberUp/MemberDown` 事件触发重分片，然后把每个节点负责的任务集合放到 Redis 里。这个方案在规模不大时能工作，但它对网络状态比较敏感，出现过网络分区、脑裂、分片状态污染和任务倾斜的问题。尤其是节点视图和 Redis 分片状态不一致时，容易出现一部分节点继续跑老任务、新任务却分不到正确节点的情况。

到了 GNC，我们把这套“依赖节点事件驱动的分片方式”，升级成了“固定分桶 + 主节点协调重分桶”的模型。简单说，就是先把任务按照稳定规则哈希到固定数量的桶里，比如 256 个桶，然后再把这些桶分配给当前在线的 schedule 实例。每个 schedule 只扫描自己持有的桶，而不是全量扫表。实例数发生变化时，由主节点基于当前实例列表重新分配桶归属，其他实例只需要刷新自己持有的桶集合即可。

这套方案的核心好处是把“任务分给谁”从动态节点事件，转成了相对稳定的桶模型。这样一来，扩缩容时我们重分的是桶，不是直接重分所有任务；调度实例之间的边界也更清晰，每个实例只处理自己的桶，避免了全量重复扫描和节点抖动带来的大范围错乱。稳定性上比 PaaS 时代的 Akka 分片更好，也更容易和云原生多 pod 部署结合。

### 可继续展开的细节

- 实例会注册心跳，主节点基于在线实例做桶分配。
- 任务是 `job -> bucket -> schedule instance` 两级映射，不是直接 `job -> instance`。
- 当实例变化时，重分的是桶归属，所以收敛更快、影响面更小。

### 一句话成果

规避了 PaaS 时代 Akka 脑裂和任务倾斜带来的稳定性风险，显著提升了多 pod 场景下的调度分配稳定性与扩缩容收敛效率。


## 3. 调度日志分表与统计体系优化

### 面试官可能会问

- 你们为什么要做日志分表？
- 100 张日志分表是怎么设计的？
- 查询和归档是怎么做的？

### 标准回答

这块主要是因为调度日志量非常大。我们平台大概有 500 个系统、10w+ 任务，生产日志规模在 2 亿级左右。如果还像原生 XXL-JOB 一样把执行日志都堆在一张表里，查询、清理和统计都会越来越慢，所以必须做分表和读写分层。

我们的设计核心是“按 system 路由到固定日志表”。基础上先预建 100 张日志分表，但不是简单平均硬分，而是在 GNC 里做了进一步优化。第一是懒分配，不是系统一同步就占一个分表，而是这个系统真正开始创建调度任务时再分配，避免很多从未使用调度的系统浪费路由资源。第二是分层资源池，把表分成热点池和普通池。热点池专门留给高频系统，普通池给一般系统。分配时会结合单表记录数、慢 SQL 情况、已绑定系统数等指标做约束，一旦某张表达到阈值，就停止新分配，把新系统导向其他表。第三是查询优化，不让用户查日志时扫全 100 张表，而是先根据系统和时间范围命中路由历史，再拼对应的少量分表；统计类场景则尽量走 `djs_statistics_*` 这些聚合表，不直接查明细。

存储层面，我们还做了冷热分层。MySQL 只保留近 90 天热数据，T-1 的历史数据归档到 OSS，归档成功并经过校验和观察期后再做删除。这样既兼顾日常排障查询，也控制了在线库体量。

### 可继续展开的细节

- 分表是围绕“系统维度查询”设计的，因为企业内部排障通常先按系统查。
- 聚合表把“写明细、读统计”分开，避免报表直接扫明细日志。
- 旧表达到阈值后不强制搬迁历史，而是新数据导向新表，降低迁移成本。

### 一句话成果

在 500 系统、10w+ 任务、2 亿级日志规模下，显著降低了全表扫描和慢查询风险，提升了日志查询、统计与存储扩展的稳定性。


## 4. 建立跨网络任务下发机制

### 面试官可能会问

- 为什么要做 Hub？
- gRPC 和 HTTP 为什么要同时支持？
- 你们的动态选路策略是怎么工作的？

### 标准回答

我们这块的核心问题是：调度器和执行器不一定在同一个网络域。尤其是海外、隔离网络、特殊机房场景下，调度服务和 worker 之间经常无法直接互通。如果只依赖直连，下发成功率会比较差，也很难兼容历史上已经接入的平台和老版本 SDK。所以我们做了一套“直连优先、Hub 兜底”的跨网络下发机制。

具体来说，调度侧不会写死某个协议或某个转发方式，而是按几类信息动态选路：执行器的 SDK 版本、当前网络可达性、系统或集群是否绑定 Hub、以及对应 worker 的运行模式。对于同网可达的新版执行器，优先走 gRPC 直连，利用长连接和 Protobuf 的性能优势做高频下发；对于历史存量执行器或者某些兼容场景，保留 HTTP 直连；如果调度器和执行器网络不通，就先访问 Hub，由 Hub 再转发给目标执行器。这样入口统一、内部协议可灵活切换。

这套设计的本质是把“可达性问题”和“协议演进问题”拆开处理。可达性问题用 Hub 解决，协议演进问题用 gRPC/HTTP 双栈兼容解决。这样业务方不需要一次性迁移所有执行器，也不会因为跨机房网络限制直接导致任务无法下发。

### 可继续展开的细节

- `schedule -> hub` 更偏治理入口，强调鉴权、限流、审计，通常走 HTTP。
- `hub -> worker` 更偏高频内部通信，强调性能，优先走 gRPC。
- 这套机制也支撑了海外和隔离网络场景下的平滑迁移。

### 一句话成果

解决了多机房、跨区域、隔离网络场景下调度器与执行器不互通的问题，显著提升了任务下发成功率和链路稳定性。


## 5. 建立执行器注册地址自动推导机制

### 面试官可能会问

- 你们为什么要做 SPI + 责任链？
- 执行器地址为什么不能让用户手填？
- 这套地址推导机制是怎么工作的？

### 标准回答

这块的背景是：我们的执行器接入形态很多，有 K8s Pod、K8s Node、VM，不同环境下真正可用的注册地址不一样。如果让业务方全部手工配置，很容易出现“本地能跑、线上不通”的情况，尤其在跨环境、跨地域、跨网络策略的场景里，地址填错的概率很高。所以我们想把地址推导这件事做成标准能力，而不是让每个业务自己试。

做法上我们用了两层设计。第一层是 SPI，负责“可插拔策略发现”。我们定义了统一的地址策略接口，比如 `IAddressStrategy`，再通过 `META-INF/services` + `ServiceLoader` 动态装载不同实现，比如 `K8s Pod`、`K8s Node`、`VM` 这几类地址策略。这样以后如果新增 IDC 专线地址、双网卡优先地址之类的新策略，不需要改核心流程，只要新增实现并注册即可。第二层是责任链，负责“流程编排”。也就是先判断用户有没有显式配置地址；如果没有，再按优先顺序尝试 `Pod -> Node -> VM` 这些策略，一旦某一步推导出可用的 `ip:port` 就短路退出，不再继续往后尝试。

这样做的价值是把复杂的环境判断从业务接入里抽出来，变成 SDK 的内建能力。业务方只要按标准方式引入 starter，启动时就能自动补齐注册地址，后续心跳注册和任务通信也都基于这个结果。

### 可继续展开的细节

- SPI 解决的是“新增策略是否要改主流程”的问题。
- 责任链解决的是“多种策略怎么按顺序尝试并可短路”的问题。
- 这套机制特别适合多部署形态共存的云原生平台。

### 一句话成果

解决了多部署形态下地址获取不一致和人工配置易错的问题，显著提升了 SDK 接入标准化、可扩展性和注册稳定性。


## 6. 调度稳定性治理

### 面试官可能会问

- 你们在原生 XXL-JOB 触发链路上做了哪些稳定性优化？
- 为什么要做快慢线程池和失败重试池隔离？
- 地址刷新和健康检查是怎么做的？

### 标准回答

这块我做的重点是围绕原生 XXL-JOB 的调度触发链路做稳定性治理。原生 XXL-JOB 本身已经有时间轮、快慢线程池、失败监控这些设计，但在我们企业级场景里，任务规模更大、网络情况更复杂，默认实现还不够，所以我主要做了三类增强。

第一类是线程池治理。原生的 `JobTriggerPoolHelper` 有快慢双池思路，但很多参数是固定的。我们把快慢线程池的核心参数做成了配置化，比如线程数、队列长度、慢任务阈值，这样可以根据 UAT 压测和线上峰值动态调整，避免高峰时触发池堆积或拒绝。另外我们还单独增加了失败重试触发池，让补偿流量和正常触发流量隔离开，防止失败风暴把主触发池拖慢。

第二类是执行器地址治理。执行器地址不是永久可靠的，尤其 K8s 场景下 Pod 可能漂移，所以我们做了地址刷新、健康检查和失活剔除。调度侧会定期聚合 registry 中的在线地址，刷新到执行器版本维度的地址列表，同时对已有地址做存活探测，失活就剔除，尽量减少调度命中脏地址的概率。

第三类是状态判定和补偿优化。比如节点下线时不只看单一事件，还引入心跳二次确认；失败任务有单独的补偿触发机制；回调异常则通过超时巡检和失败重试兜底。这样把“触发、执行、回调、补偿”四个环节串成闭环，而不是只盯着一次下发是否成功。

### 可继续展开的细节

- 快池保证绝大部分正常任务吞吐，慢池隔离慢任务。
- 失败重试池是为了避免失败流量挤占正常流量。
- 地址刷新和健康检查一起做，避免 address_list 长时间滞后。

### 一句话成果

通过线程池配置化、失败补偿隔离、地址刷新与健康检查等治理手段，显著提升了高并发和复杂网络场景下的调度稳定性与触发命中率。


## 7. 面试收尾版总结

如果面试官最后问“你这项目最核心的价值是什么”，可以统一总结成这段：

我这块工作的核心不是简单改了 XXL-JOB 的几个类，而是把原来的企业内部调度平台从单区域、单链路、偏中间件形态，升级成了一个面向多地域、多环境、跨网络场景的云原生调度平台。对外体现为多区域独立部署、海外可用、跨网络可达；对内体现为调度模型更稳、日志体系可扩展、SDK 接入更标准、稳定性治理更体系化。
