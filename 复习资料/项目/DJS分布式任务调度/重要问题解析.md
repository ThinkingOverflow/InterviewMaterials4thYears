### 1、GNC xxl-job 如何处理调度失败，怎么兜底
GNC 的失败处理不是只靠一次下发，而是把整个链路拆成几层做兜底：

**触发层失败**
- 例如：找不到可用执行器地址、Hub 转发失败、gRPC/HTTP 调用超时、目标执行器不存在对应 handler。
- 这类失败会先落调度日志，记录触发码、失败原因、路由信息、目标地址等。
- 如果任务配置了失败重试，或者平台判定属于可补偿错误，就会进入失败补偿/失败触发池，再次尝试下发。这样可以避免一次网络抖动就直接把任务判死。

**执行层失败**
- 例如：执行器收到了请求，但本地任务报异常、超时、线程被阻塞、handler 不存在。
- 执行器会把执行结果回调给调度器，调度器更新 job_log / failure_log 一类状态，并触发后续重试或告警。
- 这类失败本质上是“任务逻辑失败”，通常是否重试要看任务幂等性和业务语义。

**回调层失败**
这是最容易被问的点：执行器其实已经成功执行了，但结果没有成功返回给调度器。这种情况下，调度器一开始只知道“任务还在运行中/未完结”。

后续靠两类机制兜底：
- 执行器侧回调线程会重试回调，回调失败的任务信息保存到磁盘，有一个线程会扫描回调失败的任务然后重新回调。
- 调度器侧会有超时巡检/状态扫描，把长时间未回调的任务识别出来，标记异常或进入补偿流程。
- 这时平台只能做到“至少一次送达、至少一次补偿尝试”，但是否会重复执行副作用，最终要靠业务幂等保证。

**节点/网络层失败**
- 例如 schedule 自己重启、Hub 短时异常、执行器掉线、地址漂移。
- 平台会通过地址刷新、健康检查、失活剔除、实例心跳、重分桶/重分片来保证后续任务还能落到健康节点上。
- 对于下发瞬间失败，仍然走日志记录 + 重试 + 告警。

**GNC 的失败处理是“日志记录 + 重试补偿 + 回调重试 + 超时巡检 + 告警”五段式闭环。**

### 2、如果执行器执行成功但没有返回给调度器，怎么办

这是“执行成功、状态丢失”的最终一致性问题。

**平台侧能做的是：**
- 先把这次触发记录成唯一的调度实例
    - 每次触发都有唯一日志标识，比如 logId/triggerId。
    - 后续回调、补偿、重试都围绕这个标识更新状态。
- 执行器侧重试回调
    - 如果执行结果回传失败，不会立刻丢掉，而是由回调线程继续重试。
- 调度器侧超时巡检
    - 如果一个任务长时间处于“运行中/未回调”，调度器会把它识别为异常状态。
    - 然后根据策略决定：标记失败、发告警、或者进入补偿。
- 最终一致性靠业务幂等
    - 因为平台无法 100% 判断“业务是否真的成功落库/扣款/发消息”，所以平台只能提供唯一触发标识和补偿能力。
    - 真正避免“重复副作用”，必须业务方自己做幂等，比如唯一键、状态机、幂等表、业务流水号去重。

面试里最稳的说法是：
**平台负责至少一次投递和状态补偿，业务负责幂等消费和副作用防重。**

### 3、其他失败场景

还有哪些失败场景可以顺带提一下

- 执行器已注册但地址脏了
    - 例如 Pod 漂移了但旧地址还在。
    - GNC 通过地址刷新 + 健康检查 + 失活剔除来减少这类失败。
- Hub 可达但 worker 不可达
    - 调度器到 Hub 成功，不代表 Hub 到 worker 一定成功。
    - 这类失败也要记录在路由/触发日志里，并进入重试或告警。
- 调度器实例切换时的短暂抖动
    - GNC 用主节点选举、实例心跳、固定分桶/重分桶减少调度抖动，避免大规模漏扫。
- 失败重试风暴
    - 如果所有失败都直接和正常任务共用一个池子，会拖垮主链路。
    - 所以 GNC 把失败补偿流量和主触发流量隔离开，这是很重要的稳定性治理点。

### 4、GNC 调度时如何确保任务不会重复执行

**调度层防重复**
- GNC 的 schedule 不是所有实例全量扫任务，而是固定分桶后，每个实例只扫描自己持有的桶。
- 这样先从架构上避免多实例同时扫到同一批任务。
- dashboard/schedule 的治理任务又通过选主/单活执行，避免重复跑后台任务。

**状态层防重复**
- 任务触发会更新任务的下一次触发时间、触发日志、运行状态。
- 同一次调度对应唯一日志/触发标识，避免同一轮被多次认领。
- 如果实例变化，会通过主节点协调重分桶，而不是每个实例自己乱抢。

**执行层防重复**
- XXL-JOB 本身有阻塞策略，比如单机串行、丢弃后续、覆盖之前。
- 对于同一个任务，如果上一次还没执行完，阻塞策略决定是否允许再次下发。
- 这能避免“同一执行器上同一个任务并发跑多份”。

**业务层防重复**
- 真正的最终防重仍然要靠业务幂等。
因为即使平台已经做了分桶、防重日志、阻塞策略，遇到网络抖动、回调丢失、补偿重试时，仍可能出现“平台不确定是否成功”的场景。
- 这时业务必须基于 logId/triggerId/业务单号 做去重。

**GNC 通过“分桶扫描防多实例重复 + 唯一触发标识防同轮重复 + 阻塞策略防执行并发重复 + 业务幂等防副作用重复”四层机制来控制重复执行。**
