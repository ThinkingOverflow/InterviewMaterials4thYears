## 1、案例背景

这个案例来源于一次真实线上问题：`CBPM 接口超时问题处理及排查`。

这个问题非常适合面试，因为它不是简单的“代码写错了”，而是一个典型的：

- 表象在应用层
- 排查从 JVM 开始
- 根因最后落到基础设施层

也就是说，接口超时只是现象，真正的根因其实是底层 `NAS 网络存储性能下降`，导致应用线程在文件 IO 上阻塞，最终造成 Dubbo 调用超时。

---

## 2、问题现象

业务侧反馈：

- 美云销接口调用超时

监控告警时间线：

- `9:47`：接口调用超时
- `9:50`：开始组会排查问题
- `9:57`：通过网关和 `Spring Boot Admin` 定位到异常节点
- 异常节点为：`10.18.10.130`、`10.18.215.128`
- `9:59`：对异常节点进行现场保留和重启
- 重启服务：`cbpm-approve`、`cbpm-web`
- `10:14`：问题节点服务重启完成
- `10:16`：业务恢复可用

这个时间线在面试里很重要，因为它体现了你处理线上问题时的优先级：

1. 先恢复业务
2. 再保留现场
3. 最后做根因分析和复盘

---

## 3、前因后果

### （1）前因

系统应用日志统一挂载在 `NAS 网络存储` 上，而不是本地磁盘。

当时底层 NAS 存储中有一块硬盘故障，存储系统正在进行 `重构（自动数据修复）`，导致整个存储性能显著下降。

因为应用在运行过程中要频繁进行日志文件访问，而日志目录又在 NAS 上，所以文件系统相关操作明显变慢。

### （2）经过

应用线程在执行文件相关操作时被拖慢，进而出现：

- 部分线程拿锁执行文件 IO
- 大量业务线程等待锁
- Dubbo 线程池里大量线程处于 `Waiting` / `Blocked`
- 请求无法及时处理
- 最终上游看到接口超时

### （3）结果

最终确认根因不是：

- 代码死循环
- JVM 堆内存泄漏
- Full GC
- 普通的 CPU 打满
- 本机本地磁盘损坏

而是：

- `NAS 存储性能严重下降`
- 且下降原因是 `硬盘故障后的重构过程导致 IO 性能劣化`

厂商暂停重构后，性能恢复，接口超时问题随之恢复。

---

## 4、我是怎么排查的

这个案例建议你按“由近到远”的顺序讲：

- 先看应用
- 再看 JVM
- 再看线程
- 再看机器
- 最后看存储和外部依赖

### （1）第一步：先定位故障节点

使用工具：

- 网关监控
- `Spring Boot Admin`

目的：

- 不是一上来就看全部机器，而是先找到有问题的实例
- 缩小排查范围

定位结果：

- `10.18.10.130`
- `10.18.215.128`

### （2）第二步：先保留现场，再重启恢复业务

线上问题处理有一个原则：

`如果业务已经明显受影响，先保现场，再恢复服务。`

当时做了两件事：

1. 保留问题现场
2. 重启异常节点服务，优先恢复业务

保留现场的命令：

```bash
mkdir /apps/dump

jstack 78145 > /apps/dump/mbpm-web-stack.log
jstack 78141 > /apps/dump/mbpm-approve-stack.log

jmap -dump:format=b,file=./mbpm-web001.hprof 78145
jmap -dump:format=b,file=./mbpm-approve001.hprof 78141
```

这里可以顺便向面试官体现你的线上意识：

- `jstack` 用来抓线程栈
- `jmap dump` 用来保留堆内存现场
- 先留证据，避免重启之后线索丢失

### （3）第三步：先排除内存问题

先分析 `dump` 文件。

结论：

- 初步分析 `dump` 后，没有发现明显内存异常
- 没看到典型的堆内存泄漏特征
- 说明问题大概率不是“内存飙高导致卡顿”

这一步你面试里可以这么说：

`因为接口超时有可能是 Full GC 或内存泄漏导致的 Stop-The-World，所以我先用 dump 文件排除了明显的堆内存问题。`

### （4）第四步：分析线程栈，发现大量线程阻塞

接着分析 `jstack`。

发现：

- 大量 Dubbo 线程处于 `Waiting` 或 `Blocked` 状态

进一步看阻塞线程，发现拿到锁的线程在执行：

- `java.io.UnixFileSystem.getLength(Native Method)`

这说明什么？

这说明线程卡住不是在业务计算，也不是在 SQL，而是在 `文件系统相关调用` 上。

这是整个排查过程的关键转折点。

这一步的判断很重要：

- 如果线程都卡在业务方法，可能是代码锁竞争
- 如果线程都卡在数据库调用，可能是 DB 慢 SQL
- 如果线程都卡在网络调用，可能是下游接口
- 这次卡在文件系统原生方法，说明要怀疑 `磁盘 IO / 文件系统 / 挂载存储`

### （5）第五步：继续查服务器磁盘和文件系统

接下来开始看机器层面。

文档中提到：

- 对主机磁盘做进一步分析
- 但没有发现本地磁盘 IO 明显异常

随后继续排查发现：

- 查看目录和文件时会明显卡顿
- 通过 `df -h` 发现应用日志统一挂载在网络存储中

这里得到一个很关键的信息：

`应用虽然跑在本机，但日志落在 NAS 上，所以文件系统慢，不一定是本地磁盘慢，也可能是网络存储慢。`

### （6）第六步：验证网络存储性能

和系统工程师一起进一步确认。

验证结果：

- 在该目录下写入 `1GB` 文件，耗时超过 `1 分钟`
- 而测试环境走本地磁盘，写入 `1GB` 文件只要 `0.8 秒`

这已经非常说明问题了：

- 不是代码本身写日志太多
- 是底层存储写入性能出现严重退化

### （7）第七步：定位到 NAS 硬盘故障重构

继续登录 NAS 存储检查，发现：

- `isilon.x410 NAS` 上有一块硬盘故障正在重构

进一步判断：

- 重构过程导致存储性能下降
- 性能下降又拖慢了日志目录相关 IO
- 最终传导到应用线程阻塞和接口超时

后续处理：

1. 联系厂商协助处理
2. 暂停重构进程
3. 验证存储性能恢复
4. 晚上闲时重新进行重构
5. 重构完成后更换故障硬盘

最终问题闭环完成。

## 5、这个案例里我用了什么工具

### （1）应用与服务层工具

- 网关监控：定位哪个接口、哪台实例有问题
- `Spring Boot Admin`：看实例健康状态、线程数、运行状态、基本指标

### （2）JVM 工具

- `jstack`：分析线程状态，定位线程阻塞位置
- `jmap -dump`：导出堆快照，排查是否有堆内存问题
- `MAT` / dump 分析工具：进一步看内存对象分布和可疑泄漏

### （3）系统工具

- `df -h`：查看磁盘挂载情况，确认日志目录是否在网络存储
- 文件读写测试：直接验证目录所在存储的实际写入性能

### （4）协同排查

- 和系统工程师一起确认存储情况
- 登录 NAS 检查底层硬件和重构状态

面试里要体现一点：

`线上排障很多时候不是单纯写代码，而是“应用 + JVM + OS + 基础设施”联合定位。`

---

## 6、这个案例里我重点看了什么指标

### （1）应用层指标

- 接口 RT 是否明显升高
- 超时比例是否上升
- 是否集中在部分节点
- 服务重启后是否恢复

### （2）线程层指标

- 大量线程是否处于 `Waiting` / `Blocked`
- 阻塞线程都卡在哪个调用栈
- 是否集中在某个锁、某个类、某个外部调用上

### （3）JVM 内存指标

- 是否有明显堆占用过高
- 是否频繁 Full GC
- dump 中是否有大对象堆积、集合暴涨、泄漏嫌疑

### （4）磁盘 / 文件系统指标

- 本地磁盘是否异常
- 挂载盘是否异常
- 文件访问是否明显卡顿
- 大文件写入耗时是否异常

### （5）基础设施指标

- NAS 是否有故障
- 是否有重构
- 重构期间性能是否显著下降

## 7、最后怎么处理的

处理动作分成两类：

### （1）止血动作

- 保留线程栈和堆 dump
- 重启异常节点的 `cbpm-approve`、`cbpm-web`
- 先恢复线上业务可用性

### （2）根因修复

- 联合系统工程师确认 NAS 性能异常
- 发现硬盘故障重构导致性能下降
- 厂商暂停重构进程，恢复存储性能
- 夜间重新重构
- 后续更换故障硬盘

### （3）复盘结论

这个 NAS 比较老旧，已经降级为历史数据备份用途，不适合继续承载重要业务日志。

所以后续建议应该包括：

- 重要业务尽量不要依赖老旧 NAS
- 日志最好评估本地盘 + 日志采集方案
- 对挂载存储做独立监控和容量/性能告警

## 8、这个案例为什么适合拿来回答“CPU 飙高 / 内存飙高 / 接口超时怎么排查”

因为面试官问这类问题，真正想听的不是某条命令，而是：

- 你有没有系统排查思路
- 你会不会先保现场
- 你能不能从现象一路定位到根因
- 你是否会区分应用问题、JVM 问题、系统问题、外部依赖问题

这个案例刚好能体现：

1. 先从接口超时入手
2. 再排查 JVM 内存
3. 再看线程阻塞
4. 再看到文件系统
5. 最后定位到 NAS 存储故障

这是一个非常完整的闭环。

## 9、如果面试官追问“CPU 飙高你怎么查”

你可以在这个案例基础上顺带扩展成通用方法。

### （1）先看是机器 CPU 高还是 Java 进程 CPU 高

常用命令：

```bash
top
top -Hp <pid>
ps -mp <pid> -o THREAD,tid,time
```

排查思路：

- 先确认是不是某个 Java 进程打满 CPU
- 再定位具体是哪几个线程 CPU 高

### （2）把线程 ID 映射到 jstack

```bash
jstack <pid> > app.log
```

然后把高 CPU 的线程 ID 转成 16 进制，到 `jstack` 里搜 `nid`。

这样能找到具体卡在哪段代码，比如：

- 死循环
- JSON 序列化热点
- 大对象计算
- 锁竞争自旋
- GC 线程忙

### （3）需要看的指标

- 进程 CPU 使用率
- 单线程 CPU 使用率
- 系统 load
- GC 次数和耗时
- 请求量和 RT 变化

### （4）常见处理方式

- 修复死循环或低效算法
- 限流 / 降级
- 优化 SQL 或缓存
- 调整线程池
- 紧急扩容

## 10、如果面试官追问“内存飙高你怎么查”

### （1）先看堆内存还是非堆内存

常用命令：

```bash
jstat -gc <pid> 1000
jmap -histo:live <pid> | head -n 50
jmap -dump:format=b,file=heap.hprof <pid>
```

### （2）需要看的指标

- Old 区是否持续增长
- Full GC 是否频繁
- GC 后内存是否回不去
- 是否有大对象、缓存对象、集合对象堆积

### （3）分析工具

- `jmap`
- `jcmd`
- `MAT`
- `Arthas`

### （4）常见根因

- 内存泄漏
- 不合理缓存
- 大对象堆积
- ThreadLocal 未释放
- MQ 消息积压导致对象无法释放

### （5）常见处理方式

- 紧急重启止血
- 限流
- 调小流量入口
- 修复代码中的对象持有链
- 优化缓存策略和过期策略

你可以按下面这个模板回答：

### （1）一分钟版本

### （2）两到三分钟展开版

`如果线上出现接口超时、CPU 飙高或者内存飙高，我一般会先判断影响面和优先级，确认是不是要先止血。如果已经影响业务，我会先保留现场，比如导出 jstack、heap dump、查看日志和监控，再进行重启或摘流量。像我之前处理过一个 CBPM 接口超时的问题，当时先通过网关和 Spring Boot Admin 定位到两台异常节点，然后保留 jstack 和 dump 文件，先恢复服务。接着分析 dump，没有发现明显的堆内存泄漏；再分析 jstack，发现大量 Dubbo 线程在 Waiting 和 Blocked，最后定位到线程卡在文件系统原生方法上。顺着这个线索继续查磁盘和挂载情况，发现应用日志目录挂在 NAS 网络存储，进一步做写入测试，确认存储性能非常差。最后联合系统工程师在 NAS 上发现有故障硬盘在重构，导致性能下降，进而拖慢应用线程，最终表现成接口超时。这个问题的关键点在于，表面上看是接口慢，但本质上是基础设施存储故障。所以我现在排障会特别注意，不会一上来就认定是代码问题，而是会结合线程栈、GC、系统 IO、网络和外部依赖一起判断。`

## 12、最后你要记住的 3 个亮点

### （1）先恢复业务，再做根因分析

这体现你的线上意识。

### （2）不是只会看代码，而是会跨层排障

这体现你的工程能力。

### （3）你有“证据链”

你的排查不是拍脑袋，而是：

- 监控发现异常
- `jstack` 发现线程阻塞
- `dump` 排除内存问题
- `df -h` 发现网络挂载
- 写入测试验证存储性能差
- NAS 检查确认硬盘重构

这是非常完整的一条证据链。
